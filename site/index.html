What it enables

One brain. Many hands.
All under your eyes.

Atomic ships serious machinery — multi-stage workflows, Playwright verification, panels of independent verifiers. atomic-remote lets Claude Code drive all of it without owning it.

01Delegate heavy execution

Hand a task to Atomic and get back the finished, verified result — while its workflow (implement → static checks → browser tests → verifier panel) runs in your terminal.

atomic-ctl send auto "Build the feature,
  run your full verification workflow" --wait

02Steer without breaking flow

Priorities changed mid-run? Redirect the agent between turns — no restart, no lost context.

atomic-ctl send worker "Focus on the auth bug
  first, tests can wait" --mode steer

03Interrupt & take over

Abort the current turn and start on your instruction immediately. Deliberately a separate, explicit command — never something a model picks by accident.

/atomic-remote:interrupt worker
  "Stop. Ship the hotfix instead."

04Follow workflows to the end

Atomic answers "Workflow started" and keeps working for 20 more minutes? --wait follows the run to its terminal notice. Intermediate text is never sold as the result.

note: workflow launched (342cb4e9…)
      — waiting for its terminal notice

05Command a fleet by name

Every session self-registers with a stable identity and auto-names itself after its project. Target by name, id, or cwd — auto when there's only one.

atomic-ctl list
  api-server    live  idle  proto=3
  frontend      live  busy  proto=3
  data-pipeline live  idle  proto=3

06Observe everything, always

A durable, per-session event log: every command, turn, owner and workflow notice. follow streams it live; tail reads it even after the session closed.

atomic-ctl follow api-server

07Ship a workflow, don't describe it

Hand Atomic an executable workflow file: the bridge installs it, reloads discovery and runs it deterministically — with a structured plan (goal, constraints, acceptance criteria) attached.

atomic-ctl run-workflow api-server \
  release-check.ts --wait

08Unblock a run waiting on you

A workflow stopped on a human question is detected — exit 7 says awaiting human input, not "still working" — and answerable from Claude Code.

atomic-ctl answer api-server \
  342cb4e9-… "yes, ship it"
The story

Born live. Hardened by agents.

This plugin wasn't designed on a whiteboard — it was built, broken and rebuilt in one live session.

Built against the official docs day 1

v1 written from Atomic's extension & RPC documentation: a file bridge, injection via pi.sendUserMessage, four command modes. First end-to-end test passed on a real session.

The live demo day 8

Claude Code opened a terminal, commanded Atomic to build a snake game — and Atomic answered by launching its own multi-stage workflow: implementation, static checks, Playwright simulating arrows, collisions and game-overs, then three independent verifiers. The game shipped. 1,284 lines, one file.

The demo found the flaw same session

--wait printed "Workflow started" as if it were the result. Plausible, wrong, and exactly the kind of bug that silently poisons automation.

An adversarial review by 8 agents day 8

Five analysis lenses (protocol, capabilities, security, DX, autonomy) produced 30 proposals. An API-reality verifier checked every claim against Atomic's official docs; a value skeptic killed the over-engineering. Five survived — the full review is in the repo.

Protocol v2 shipped & verified same day

Heartbeat liveness, attributed replies, workflow-aware waits, fail-closed inbox, durable history. Re-tested end-to-end against a live session before the first public commit.

Protocol v3: structure over prose next cycle

The plan→execution handoff got typed: structured plan artifacts (--plan), deterministic workflow entry (run-workflow), real slash-command dispatch, queryable outcomes (outcome) and a typed workflow lifecycle replacing keyword regexes.

0.3.1: the full-docs audit latest

A second adversarial cycle against Atomic's complete documentation. Attribution made theft-proof (TTL-bounded bindings, structural preemption discriminator), human-input detection with the answer command, a two-lane queue so abort never waits behind a workflow install, total event ordering, and command-surface validation via getCommands(). 83 → 115 tests, every fix red-then-green.

Protocol v3

Replies you can trust.
Failures you can tell apart.

Automation dies on ambiguity. The protocol's whole design goal is that a program — or a model — can act on the bridge's answers without guessing.

◈Attributed replies

Commands bind to their turn via Atomic's documented input event; every record carries an owner id and a monotonic seq. --wait concludes on agent_settled — the real terminal event — for your command. Bindings are TTL-bounded (an expired one fails loud, never captures a later turn), aborted turns can't steal an interrupt's reply, and concurrent TUI typing refuses (exit 6) rather than hand you someone else's answer.

◈Heartbeat liveness

Sessions are live stale closed by a 5-second beacon — not by a transient engine pid that Atomic legitimately replaces. Delivery to a dead bridge is refused up front, not discovered by timeout.

◈Nothing deleted implicitly

list is read-only. History survives shutdown. Cleanup only happens through the explicit prune command — closed sessions only, symlink-escape guarded.

◈Fail-closed inbox

Schema-validated commands with typed reject reasons, O_NOFOLLOW + regular-file + 64 KiB caps, strictly serial processing, at-least-once delivery with restart recovery. Every command is acknowledged — malformed ones included.

Quickstart

Two sides. Two minutes.

The plugin lives in Claude Code; a tiny extension bridges into Atomic. Both installs are one command.

STEP 01

Add the plugin to Claude Code

claude plugin marketplace add \
  uppifyagency/atomic-remote
claude plugin install \
  atomic-remote@atomic-remote
STEP 02

Bridge into Atomic

From Claude Code, then reload inside Atomic:

/atomic-remote:setup
# inside the Atomic session:
/reload
# → atomic-remote bridge v0.3.1 active
STEP 03

Command it — or just ask

/atomic-remote:send auto \
  "Run the tests, fix failures" --wait

Or plain natural language — the bundled skill teaches Claude the entire flow, exit codes included.

Security model

Powerful means dangerous. Treat it that way.

The inbox is arbitrary command execution with your user's permissions. That is the feature — and the threat model. atomic-remote keeps the surface minimal: strictly local file transport (no ports, no daemons, no network), directories created 0700, files 0600, symlink-refusing ingestion, size caps, and an outbox that is protected like the code it contains. Never widen the permissions. Never forward a network listener into the inbox.
